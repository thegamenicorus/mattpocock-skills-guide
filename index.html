Matt Pocock Skills

How to use these skills in actual daily dev work

This guide is not a repo summary. It is a practical operating manual for using the skills as a software developer: shaping a feature, fixing a bug, spinning up a prototype, writing tests, understanding an unfamiliar codebase, and keeping work ready for async agent execution.

Core frame: treat the agent as a junior engineer with weird constraints, not smart autocomplete. The skills encode the senior-engineer habits that keep that junior productive — slow down, build context, write one test at a time, then zoom back out.

GitHub Repo Skill Reference
Default flow
  1. Install the skill pack.
  2. Run /setup-matt-pocock-skills once per repo.
  3. Use the workflow recipe that matches your task.
  4. Prefer small vertical slices over big all-at-once implementation.

Mental Model

  • Grill: remove ambiguity before coding.
  • Prototype: answer a question with throwaway code.
  • PRD / Issues: turn decisions into executable work.
  • TDD / Diagnose: use feedback loops instead of guessing.
  • Zoom Out: understand system shape before changing it.

Caveats

  • Stack bias: skills lean TypeScript / Node + GitHub issues. Django, GitLab, or other setups may need a forked skill.
  • Model strength: grilling skills can bail or refuse on smaller / non-frontier models. Use Claude or GPT frontier tiers for best results.
  • Install lean: only enable the skills you'll actually use. A bloated skill set hurts the agent's intent matching.

New Feature

Best when you want disciplined delivery instead of “build everything from a vague prompt”.

Best chain grill-with-docs → to-prd → to-issues → tdd
  • 1. Stress-test the idea: use /grill-with-docs so the agent asks one question at a time and reconciles your plan with existing repo language in CONTEXT.md and ADRs.
  • 2. Freeze the shape: use /to-prd to turn the current conversation into a PRD without another interview.
  • 3. Break into slices: use /to-issues so implementation tickets are thin vertical slices, not “backend first, frontend later” horizontal chunks.
  • 4. Build safely: use /tdd to implement one observable behavior at a time through public interfaces.
Expect grilling to be substantial — 15–40 questions is normal, not a quick chat. That is the point: the agent surfaces every decision you would otherwise hit during coding, where it costs ten times more to fix.

Why This Works

The pack tries to eliminate the two common failures: unclear feature intent and giant speculative implementation. It forces decisions to solidify before coding.

Important Rule

/tdd explicitly rejects horizontal slicing. Do not write all tests first and all code second. Do one test, one implementation, repeat.

Example prompt 

We need saved drafts for long support replies. Use /grill-with-docs to challenge the idea against existing inbox rules. When the shape is clear, run /to-prd, then /to-issues, then build the first AFK slice with /tdd.

Bug Fix

Use this when a defect is real but the cause is still unclear, or when you need a repeatable regression test before claiming the fix.

Best chain zoom-out → diagnose → tdd
  • 1. If the area is unfamiliar: run /zoom-out first to get a map of relevant modules and callers.
  • 2. Build a feedback loop: run /diagnose. Its core rule is: do not guess before you have a reproducible pass/fail loop.
  • 3. Rank hypotheses: the skill pushes you to generate several falsifiable hypotheses before changing code.
  • 4. Fix and lock it down: once you have the right seam, turn the minimized repro into a failing regression test and use /tdd if the repair expands into behavior work.
The strongest idea in /diagnose: a fast deterministic loop is 90% of the bug fix. No loop, no serious debugging.
Example prompt 

Customers sometimes hit a timeout on checkout after entering a promo code. Use /zoom-out if needed, then /diagnose. Once you confirm the root cause, switch to /tdd, add a failing regression test, fix it, and keep the change minimal.
Template 

{your problem}
Use /zoom-out if needed, then /diagnose. Once you confirm the root cause, switch to /tdd, add a failing regression test, fix it, and keep the change minimal.

Craft A New Project

There is no single “new project” skill here. The repo expects you to compose a project workflow from planning, prototype, and delivery skills.

Best chain grill-me → prototype → to-prd → to-issues → tdd per issue
  • 1. Clarify the product: use /grill-me if you want a relentless interview without repo-document updates yet.
  • 2. Prove the risky idea: use /prototype to answer the hardest question first, either logic/state or UI direction.
  • 3. Turn it into an artifact: use /to-prd once the concept stops moving.
  • 4. Turn strategy into slices: use /to-issues so the first build steps are independently shippable.
  • 5. Build one issue at a time: take the first AFK-ready slice, use /zoom-out if the code area is unfamiliar, then implement that issue with /tdd.
  • 6. Repeat until the project exists: close each issue, pick the next slice, and use /handoff between sessions if another agent or future-you needs to continue.

When To Prefer Grill-Me

Use it before code exists, or when you want pure design pressure-testing without touching CONTEXT.md and ADRs yet.

When To Switch To Grill-With-Docs

Use it once a repo exists and your terminology should align with the existing domain language and documented architectural choices.

Important: /to-issues is not the end of the project. It is the handoff from planning into execution. After that, your working loop becomes: pick one issue, implement it with /tdd, close it, then move to the next slice until the product is complete.
Example prompt 

I want an internal approvals dashboard, but the scope is fuzzy. Start with /grill-me. When we know the riskiest assumption, use /prototype. If the concept holds up, create the PRD and issues. Then take the first AFK-ready issue, implement it with /tdd, and continue issue by issue until the dashboard is usable end to end.
Template 

{your project idea, product concept, or internal tool idea}
Start with /grill-me. When we know the riskiest assumption, use /prototype. If the concept holds up, create the PRD and issues. Then take the first AFK-ready issue, implement it with /tdd, and continue issue by issue until the project works end to end.

Legacy / Unfamiliar Codebase

New job, inherited service, or a repo that grew faster than its docs? Do not apply the greenfield flow. The agent cannot respect architecture that only lives in your head.

Best chain improve-codebase-architecture → grill-with-docs → zoom-out → normal flow
  • 1. Survey the terrain: run /improve-codebase-architecture to surface the muddiest seams and the highest-leverage deepening opportunities. You are not refactoring yet — you are forming a map.
  • 2. Seed the shared language: use /grill-with-docs to create or extend CONTEXT.md. Capture domain terms now, before the agent has to invent them on the fly.
  • 3. Zoom in only when needed: use /zoom-out on the specific module you will touch first, so the change lands with full awareness of callers and boundaries.
  • 4. Resume normal flow: once context exists, switch into the feature or bug recipe. The setup pays back across every subsequent session.
Skipping straight to /tdd in a legacy codebase produces tests that pass against the agent's guess of the system, not the system itself. Establish context first.
Example prompt 

I just inherited this service and need to add a new endpoint. Use /improve-codebase-architecture to map the muddiest seams, then /grill-with-docs to seed CONTEXT.md with the domain language you find. After that, use /zoom-out on the area I'll touch first, then switch into the normal feature flow.
Template 

{the inherited service, legacy module, or unfamiliar repo you need to change}

PoC / Prototype

This is one of the repo’s clearest and most useful skills. Prototype code is meant to answer a question, not quietly become production code.

Best skill prototype

Logic Branch

Use when the question is: “does this state machine, workflow, or domain model behave correctly?” Build a tiny interactive terminal app.

UI Branch

Use when the question is: “what should this look like?” Build multiple radically different variants on one route, switchable by URL param.

Rules

One command to run. No persistence by default. Minimal polish. Surface the full state after each action. Delete or absorb the result when the question is answered.

Example prompt 

We are unsure whether onboarding should feel like a wizard or a checklist. Use /prototype to create two radically different UI variants on one route. Keep it throwaway and capture the decision signal we learn from it.
Template 

{your design question or risky assumption}
Use /prototype to create a throwaway prototype that answers the question quickly. If this is a UI question, create multiple radically different variants on one route. Keep it throwaway and capture the decision signal we learn from it.

Testing

The repo’s testing posture is strongly behavior-first. It prefers tests that survive refactors because they verify public behavior, not private structure.

Best skill tdd
  • Tests should use public interfaces.
  • Tests should describe what the system does, not how internals are wired.
  • Good tests are usually integration-style and survive internal refactors.
  • Each red-green cycle should cover one behavior only.
  • Refactor only when the suite is green.

Use It For

New behavior, bug fixes with a clear seam, and any change where you want a disciplined red-green-refactor loop.

Avoid

Mock-heavy tests tied to internal collaborators, private methods, or internal call graphs. If renaming internals breaks tests, the tests are too coupled. And resist bulk-writing tests up front — that verifies imagined behavior, not observed behavior. Let each test discover the next one.

Example prompt 

Use /tdd for this feature. Confirm the public interface and the highest-value behaviors first, then implement one tracer-bullet behavior at a time with integration-style tests.
Template 

{your feature, fix, or behavior change}
Use /tdd. Confirm the public interface and the highest-value behaviors first, then implement one tracer-bullet behavior at a time with integration-style tests.

Codebase Maintenance

This repo is not only about shipping features. It also assumes agent-assisted development can accelerate codebase entropy if you never zoom back out.

Best skills improve-codebase-architecture + triage + handoff
  • Improve architecture: run /improve-codebase-architecture every few days to look for deeper modules and places where the system is turning into a ball of mud.
  • Feed your CONTEXT.md: revisit it whenever new terms, modules, or decisions land. Treat it as a living glossary, not a one-time export.
  • Triage incoming work: use /triage if your workflow depends on issue states like needs-triage, ready-for-agent, and wontfix.
  • Stop losing context: use /handoff when another session or another agent needs to continue the work cleanly.
Context decay is real: skip a week of edits to CONTEXT.md and ADRs and the agent's accuracy regresses fast. The shared language is only powerful while it stays current with the code.
Good daily use is less about memorizing every skill and more about learning a few stable chains you can reuse: clarify, slice, build, verify, then zoom back out.
Templates 

{codebase area getting muddy, shallow, or hard to change}
Use /improve-codebase-architecture to find the highest-leverage deepening opportunities in this area.

{incoming issue or backlog item}
Use /triage on this and move it to the right state with a durable comment for the next person or agent.

{work that another session or agent must continue}
Use /handoff so the next agent can pick this up without losing context.

Common Mistakes

These skills are opinionated. They are strongest when you obey the intended constraints.

  • Do not skip /setup-matt-pocock-skills and then expect issue-based workflows to behave correctly.
  • Do not use /tdd as “write a full test suite, then fill in implementation later”.
  • Do not use /diagnose as an excuse to brainstorm without a reproducible loop.
  • Do not let prototype code quietly become production without either deletion or a deliberate absorption step.
  • Do not use /grill-with-docs without caring about domain language and ADRs. That is the point of the skill.

Simulated Sessions

These are the examples the earlier prompts were missing: realistic flows from the first user message to a solved outcome, including when the skill chain switches.

Bug Fix: Checkout Timeout

User

Customers sometimes hit a timeout on checkout after entering a promo code. Use /zoom-out if needed, then /diagnose. Once you confirm the root cause, switch to /tdd, add a failing regression test, fix it, and keep the change minimal.

Agent

First it maps the checkout flow, identifies the promo-code path, and builds the fastest reproducible loop. Then /diagnose ranks hypotheses such as retry storms, stale pricing cache, or promo validation deadlock.

Agent

After instrumentation, it proves the timeout happens when promo validation calls pricing twice under one request. At that point the chain changes: it switches to /tdd, writes the failing regression test around checkout with a promo code, applies the smallest fix, and reruns the suite.

Done

You get a root-cause explanation, the regression test, the code fix, and confirmation that the deterministic repro loop now passes.

New Feature: Saved Drafts

User

We need saved drafts for long support replies. Use /grill-with-docs to challenge the idea against existing inbox rules. When the shape is clear, run /to-prd, then /to-issues, then build the first AFK slice with /tdd.

Agent

It asks one question at a time: per-user or shared drafts, autosave timing, conflict behavior, retention, and whether drafts belong to threads or replies. It checks existing domain docs and ADRs before asking questions already answered in the repo.

Agent

Once the decisions stop moving, /to-prd turns the conversation into a stable artifact. /to-issues then slices the work into vertical units such as draft persistence, editor restore, and draft conflict handling. The first slice is implemented via /tdd.

Done

You end with a clarified feature, a PRD, actionable issues, and one shipped slice backed by behavior-first tests.

PoC: New Onboarding Flow

User

We are unsure whether onboarding should feel like a wizard or a checklist. Use /prototype to create two radically different UI variants on one route. Keep it throwaway and capture the decision signal we learn from it.

Agent

/prototype chooses the UI branch, creates multiple variants, and makes them easy to switch between with a URL parameter. It keeps persistence and polish minimal because the goal is comparison, not production readiness.

Agent

After review, it summarizes the tradeoff: for example, the wizard reduces cognitive load for new users, while the checklist makes progress resumable and transparent. It records which variant won and why.

Done

You get a decision, not just a mockup. The next step is either delete the prototype or convert the chosen direction into a PRD and issues.

Greenfield Project: Internal Tool

User

I want an internal approvals dashboard, but the scope is fuzzy. Start with /grill-me. When we know the riskiest assumption, use /prototype. If the concept holds up, create the PRD and issues.

Agent

/grill-me narrows the problem: approver roles, SLA expectations, queue size, escalation, and reporting needs. It recommends answers and challenges weak assumptions one branch at a time.

Agent

It identifies the riskiest assumption as queue triage usability, so /prototype builds a minimal interaction model first. If the model works, /to-prd and /to-issues convert the idea into a buildable roadmap.

Agent

Then execution begins: it picks the first AFK-ready issue, uses /tdd to implement that vertical slice, closes it, and repeats slice by slice until the approvals dashboard works end to end.

Done

You move from fuzzy idea to validated direction to implementable slices, then to a real working project built one issue at a time.

All Skills In Detail

Every current skill in the repository, grouped by category. This section is for the “what exactly does this one do?” question, not just which workflow to chain.

Engineering Skills

Core execution skills for planning, implementation, debugging, issue slicing, and architecture work.

/setup-matt-pocock-skills

Use when: setting up a repo for the first time.

What it does: configures issue-tracker integration, label mapping, and how domain documentation is organized so the other skills have context.

Constraint: this is the prerequisite skill; the planning and triage skills depend on it.

/grill-with-docs

Use when: shaping a feature in an existing repo where ADRs and domain docs matter.

What it does: asks one question at a time, checks the repo first so it does not re-ask anything already answered in CONTEXT.md or ADRs, then writes new decisions back into those docs. Proposes ADRs only for major calls.

Constraint: this is for repo-aware planning, not casual ideation.

/to-prd

Use when: the conversation is mature enough to be frozen into a PRD.

What it does: turns discussion into a product artifact with problem framing, user stories, technical decisions, and testing notes.

Constraint: it prefers durable intent over code-level implementation trivia.

/to-issues

Use when: you need execution-ready issues from a PRD or design conversation.

What it does: creates small vertical slices, flags AFK vs HITL work, and orders issues by dependency.

Constraint: it rejects horizontal slicing as the default breakdown.

/tdd

Use when: implementing behavior through a disciplined feedback loop.

What it does: pushes red-green-refactor with public-interface, integration-style tests and one tracer-bullet behavior per cycle.

Constraint: avoid implementation-coupled tests and “write all tests first” workflows.

/diagnose

Use when: a bug is real but the cause is unknown.

What it does: forces you to create a reproducible loop, rank hypotheses, instrument the system, verify the root cause, then lock the fix with a regression test.

Constraint: no serious debugging without a loop you trust.

/zoom-out

Use when: you are entering an unfamiliar code area.

What it does: maps modules, boundaries, callers, and project glossary terms before you make a local change.

Constraint: use it before a risky change, not after you have already gone tunnel-vision on one file.

/prototype

Use when: you need to answer a question quickly with throwaway code.

What it does: branches into logic prototypes or multi-variant UI prototypes, optimized for learning rather than polish.

Constraint: prototype output should be deleted or deliberately absorbed later.

/triage

Use when: sorting incoming issues or preparing them for async agent execution.

What it does: applies a state machine to labels, reproduces when possible, and writes structured issue comments for maintainers or agents.

Constraint: relies on the label conventions configured during setup.

/improve-codebase-architecture

Use when: the repo is getting shallow, scattered, or harder to reason about.

What it does: searches for high-leverage refactors that deepen modules and improve locality while staying aligned with repo vocabulary and ADRs.

Constraint: it starts by identifying candidate opportunities, not by inventing abstractions in the abstract.

Productivity Skills

Conversation-shaping skills for clarification, brevity, continuity, authoring custom skills, and structured learning.

/grill-me

Use when: an idea is fuzzy and you want a direct interview without the repo-document coupling of /grill-with-docs.

What it does: asks one question at a time, recommends an answer with each question, and resolves uncertainty aggressively.

Constraint: this is the generic planning interrogator, not the repo-aware one.

/caveman

Use when: you want low-token, terse responses during pairing or rapid iteration.

What it does: switches the agent into compressed communication mode while preserving correctness.

Constraint: the mode persists until explicitly disabled.

/handoff

Use when: another session or agent must continue the work.

What it does: writes a compact handoff summary to a temp file, references existing artifacts, and recommends next-step skills.

Constraint: it is meant to minimize duplication, not create another giant document.

/write-a-skill

Use when: you want to create a custom reusable skill.

What it does: gathers requirements, drafts the SKILL.md, and emphasizes clear trigger descriptions so the agent knows when to use it.

Constraint: vague descriptions make the skill hard to trigger accurately.

/teach

Use when: you want to learn a topic progressively across multiple sessions in a dedicated workspace.

What it does: treats the working directory as a teaching workspace, capturing a MISSION.md, curated resources, learning records, and beautiful self-contained HTML lessons that target your zone of proximal development.

Constraint: stateful — relies on the workspace files surviving between sessions, and never trusts the agent's parametric knowledge over cited resources.

Personal Skills

Writing and knowledge-management skills tuned for personal workflows.

/edit-article

Use when: you have an article draft that needs restructuring or prose tightening.

What it does: splits the article into sections, confirms the structure as a dependency-ordered flow, then rewrites each section for clarity with a paragraph-length budget.

Constraint: works section-by-section with check-ins, not as a single one-shot rewrite.

/obsidian-vault

Use when: you want to find, create, or organize notes inside your Obsidian vault.

What it does: searches the vault, writes flat title-case notes, and keeps things connected through [[wikilinks]] and index notes rather than folder hierarchies.

Constraint: assumes the vault path and naming conventions configured in the skill — adjust if yours differ.

Misc Skills

Specialized utilities for setup, migration, exercise scaffolding, and defensive tooling.

/git-guardrails-claude-code

Use when: you want Claude Code protected from destructive git commands.

What it does: installs hooks that block risky commands such as force pushes, hard resets, aggressive cleans, and destructive branch deletion.

Constraint: geared specifically toward Claude Code hook-based workflows.

/migrate-to-shoehorn

Use when: test code contains too many ugly TypeScript assertions.

What it does: migrates tests to @total-typescript/shoehorn helpers like fromPartial() and fromAny().

Constraint: it is for test code, not production code.

/scaffold-exercises

Use when: you are building workshop or course exercises with consistent folder conventions.

What it does: scaffolds numbered exercise structures and iterates until the exercise linter passes.

Constraint: useful mainly for repos that already follow this training-content layout.

/setup-pre-commit

Use when: a JS/TS repo needs commit-time formatting and safety checks.

What it does: wires Husky, lint-staged, and Prettier into a pre-commit workflow, adapting to the package manager it finds.

Constraint: it uses only scripts that already exist instead of inventing missing test or typecheck commands.
